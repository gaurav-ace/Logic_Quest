## Phase 2, Rewards and progress (done 2026-10-19)

- 2.1 Reward engine (`src/rewards/`): progress is an event log, and XP, level, streak, coins and badges are computed from it by pure functions. XP comes only from correct answers (10 first try, 5 after a retry, 10 for first completing a lesson; never negative, each question scored once). Streak coins: +5 per goal day; one missed day uses a buffer (−15), a second breaks the streak (−25); never below 0. 18 config-driven badges. All numbers in `src/rewards/rewards.config.json`, validated at load. Lessons now have `track` and `level`. 56 new tests, plus mutation checks on anti-farming, the coin floor and "today is never a miss".
- 2.2 Progress storage (`src/progress/store.ts`): versioned save in localStorage; every write re-reads and merges by event id, so two open tabs never overwrite each other; an unreadable save is copied to a backup key and reported, never silently dropped (and never overwritten if the copy fails); full or blocked storage keeps progress in memory with a notice. Export to JSON and import with a preview; importing merges, so the same file twice adds nothing. 18 tests.
- 2.3 Rewards in lessons: the quiz records every answer and completion (`src/progress/tracker.ts`, tested) and shows what it earned, one line each ("+10 XP, first try", "Lesson complete: +10 XP. Today's goal is done.", badges). Replays say "Already scored". One reward pop-up per answer (none in calm mode, no animation with reduced motion). The home screen shows level, XP bar, streak, coins and today's goal with a plain streak message, and marks finished lessons ✓ Done. Leaving a finished quiz no longer asks first. Progress from another tab is merged live.
- 2.4 Progress screen (`#/progress`, `src/render/progress.ts`): level and XP, current and best streak, a 7-day view (goal met, buffer, broke, missed, today), the coin rules in plain words, all 18 badges (earned with date, locked with what it takes), settings (daily goal 1–3, calm mode), and backup: export downloads a JSON file; import previews how many new items a file adds, then merges (the same file twice adds nothing; a bad file is rejected with the reason). Browser checks: 105 UI + 7 PWA.
- Persistence across launches: the app asks the browser for persistent storage (so saved progress isn't cleared when space runs low) and the progress screen says whether it was granted. New `browser-check.mjs persist` mode closes and relaunches Chrome on the same profile on simulated later days and checks that XP, streak, coins and finished lessons resume, and that the buffer and streak break apply.

## Phase 4, Data structures and algorithms (done 2026-10-19)

- 4.1 New trace views: stack, queue, linked list (arrows may point back or loop), hash buckets, tree (binary in-order layout, or n-ary for tries) and graph (weighted or directed edges, per-node notes), plus a highlighted table cell. SVG views are drawn at real pixel size so labels stay at least 14 px on a phone; wide ones scroll inside their own box. Every view also writes a screen-reader sentence. Tree layout is a pure function, tested on 100 random BSTs (left < parent < right, one row per depth, no shared columns, safe on cycles in bad data).
- 4.2–4.4 Thirty DSA lessons (D1–D30), every one a computed trace: Big-O by counting, time versus space, arrays, two pointers, sliding window, prefix sums, linked lists, fast and slow pointers, stacks, monotonic stack, queues and deques, hash maps, counting and grouping, binary search, binary search on the answer, simple sorts, merge sort, quick sort, heaps, recursion, backtracking, tree traversals, binary search trees, tries, BFS, DFS and islands, topological sort, Dijkstra, union-find, dynamic programming. Each program is checked against a reference on 200 random inputs, and where possible that reference is a different algorithm (bracket deletion, brute-force next greater, visited-set cycle check, BFS islands, Bellman–Ford, all-pairs hop relaxation, graph search for union-find, BFS coin change). Claim tests cover what the lessons teach, for example ⌊log₂ n⌋ + 1 binary-search checks, merge sort stability, quick sort's O(n²) on sorted input, the heap rule after every push, valid topological orders, Dijkstra settling in distance order, and greedy coins losing on {1, 3, 4}. `requires` builds the ladder (Dijkstra needs BFS, DP needs recursion, and so on). Built together and committed as one change because the batches share the registry, catalog and claim tests.
- Phone layout fixes found by the browser checks: real-size SVG views were being scaled down by an old diagram rule (text shrank to 9.9 px); wide arrays pushed the page sideways (grid items now shrink); graph positions now fit the 304 px content width; array cells are capped at 64 px; labels over lines get a halo. The label-size check now measures every SVG's real scale. New `lessons` mode (with `LESSONS=a,b`) walks chosen lessons only.
- Fix: the installed app on Android kept showing the old version after a deploy. Pages now load network-first (3 s timeout, cached copy offline), the app checks for an update whenever it returns to the front and hourly, and a "Reload" banner appears when a new version takes over while the app is open (never an automatic reload mid-lesson). New `browser-check.mjs update` mode simulates a deploy: it failed against the old service worker and passes now.

## Phase 5, System design (done 2026-10-19)

- 5.1 Simulation lessons (`kind: "sim"`): a seeded, pure model runs in simulated time; the learner moves sliders, flips switches and injects failures (kill a server, flush a cache), and watches live numbers with small history charts. Challenges have a prediction first, a goal checked as the sim runs ("errors ≤ 1% for 15 s", or "the whole time" for sudden events), XP on success, and locked settings. Pause/Play, 1x/2x/4x and Reset sit in the bottom bar; the sim freezes when the tab is hidden. Shared request-flow core (`src/sim/requests.ts`): arrivals, routing, queues, timeouts, failures, with bookkeeping tested every tick (no request lost or double-counted). Every challenge is tested to be winnable with its hidden solution (on the app's exact run and two other seeds) and not passable from its starting setup; the measurements behind each goal are in the session log.
- 5.2 Traffic lessons: How a request travels (diagram with predictions: DNS, TCP, TLS, HTTP), Scaling up versus out (sim), Load balancing under pressure (sim: round robin versus least connections, health checks with a detection delay, kill a server), Caching in action (sim: cache size, stale reads and invalidation, cold-restart stampede and coalescing), CDNs (sim: edges near users, origin load). Model claims tested on fixed seeds. Fixes found on the way: latencies were one tick too short; deep-copying state every tick was too slow for a phone (now copies only what changes); sim labels overflowing boxes (the label check now covers sim nodes).
- 5.3 Data lessons: SQL versus NoSQL (diagram with predictions), Indexes (computed trace: full scan versus a sorted index with binary search; tested to find the same rows within log₂ n + 1 + matches checks), Replication (sim: stale follower reads, failover, lost writes with asynchronous copying versus synchronous), Sharding (sim: hash sharding, the hot key that more shards can't fix), Consistent hashing (computed trace: only keys next to the new server move, all to it; tested on 500 random rings against key % N). Model bugs caught in review: resharding dropped in-flight requests silently, a synchronous write with no follower waited forever, and a dead leader still "delivered" copies it never sent (which hid the lost-writes effect).
- 5.4 Reliability and design lessons: Message queues (sim: absorb a burst with queue size, more workers when a queue can't keep up, a dead-letter queue for poison messages), Rate limiting (computed trace: fixed window versus token bucket; the boundary burst that lets 2× the limit through a fixed window), CAP and consistency (sim: cut the network, then choose refusing writes or letting the copies drift), Idempotency and retries (sim: lost replies, retries that double charge, idempotency keys that stop it), Design: URL shortener and Design: AI chat service (design-review diagrams with predictions). 58 lessons in all.
- Fix (found in 5.4, shipped in 5.3): sharding notes ("43% of traffic") were cut off at the diagram's right edge, and a column of 4 servers or shards had no room for its notes. Shared column layout (`columnYs`), the sim diagram grows to fit its lowest note, boxes moved off the edge. The new browser check also found the topological-sort graph's "waits 0" notes running past both sides (since Phase 4); the end nodes moved inward. New checks that fail on the old code: a unit test that nodes and notes stay inside and don't overlap, at the default settings and with every slider at max; and a browser check that no text or box is drawn past any SVG's edge.

- 5b.4 Design problems: Design: parking lot (requirements to classes, the park sequence, fee policies as strategies, the two-gates race), Design: LRU cache (a computed trace of a hash map plus linked list, checked against an independent insertion-ordered-map reference on 200 random inputs, and on 300 more that it never exceeds capacity and always evicts the least recently used key; a mutation that evicts the newest key fails 3 tests), Design: rate limiter class (per-user token buckets with a clock passed in; its reference is S12's tested token bucket run per user; tests show one user's traffic never changes another's results and at most 2 × rate requests pass in any second), Design: tool-calling agent (loop, model, tools, memory and guardrail as separate parts; a sequence diagram of one turn; testing with a scripted fake model). 72 lessons in all.

## Phase 6, Agentic AI (built 2026-10-20, awaiting the owner's review)

- 6.1 Engine: a new lesson kind, `agent`. A scripted model (plain rules, shown on screen; no real AI and no API calls) works through a task in a loop over a small fake world: it decides, guardrails check each call before its tool runs (block, or send to a scripted reviewer), the tool runs, and the result, the error, or an empty result when errors aren't passed on goes back into its context. The runner (`src/agent/runner.ts`) owns the step limit, a context budget with compaction, notes, and illustrative token counts, and records frames in the trace format, so runs step turn by turn with "what happens next?" predictions computed from the run. A panel shows the run's outcome, the current challenge and the settings ("Run with these settings"); challenge goals are checked on one run's outcome, and every challenge is tested to pass with its solution and not from its setup. Runner invariants are tested on 300 random settings per scenario (ends once, respects the limit, counts only go up, repeats exactly); a test-only scenario shows blocked or rejected calls never reach their tool and the context stays within budget. New browser mode `agent`.
- 6.2 A1 Prompt in, text out (diagram); A2 Tool use; A3 The agent loop: limits and failures; A4 Memory (keep everything, compaction, or notes, at different context budgets); A5 Planning (a stale plan followed blindly).
- 6.3 A6 Workflows versus agents (diagram with a critique); A7 Guardrails (indirect prompt injection; marking tool text as data, human approval above a threshold, an email allow-list); A8 Failure modes (flaky tool, stuck tool, invented argument, wrong tool, each with the guardrail that catches it).
- 6.4 A9 Multi-agent systems (parallel workers: speed, token cost, duplicated work, too many workers); A10 Evaluating agents (a computed regression eval of the A8 agent). 103 lessons in all.
